Purpose and scope
This catalogue defines 12 domains and 30+ separate modules for Al Qarib's corporate
banking and Global Transaction Banking (GTB) offer. Each module is sold and switched on
only through a signed bank agreement, with its own transaction types, user limits and
corporate daily and monthly limits.

        Segments: Large, Medium and Small corporates each get a default package; the bank
        admin can override any value per agreement.
        Rails: instant payments run on LYPay, domestic batch and cheques on ACH, large
        values on RTGS, cross-border on SWIFT.
        Reading a module: every spec has the same blocks: description, transaction types,
        users and roles, agreement terms, limits, controls.
        Status: all limits and rail ceilings are parameters to be set; none are final figures. Items
        awaiting CBL confirmation are listed in the last section.

Platform model: agreements, limits and roles
No module works until the bank admin activates it in a signed agreement, and every
transaction is checked against five limit levels; the lowest applicable one wins.

Limit levels (checked in this order)
   1. Rail ceiling: a system parameter per rail, such as the ACH amount cap, held as a
       configurable value until CBL confirms it.
   2. Module and transaction-type limit: per transaction, daily and monthly, set in the
      agreement.
   3. Corporate limit: daily and monthly totals per module, plus an overall corporate total
       across all modules.
   4. User limit: per transaction and per day, set by the corporate admin per user, never
       above the corporate limit.
   5. Approval matrix: amount bands decide how many checkers must approve before
       release.

Limits for trade finance and credit cards count outstanding exposure instead of money
moved per day.

Domain 4: Virtual account management

every incoming payment is matched to a customer, branch or invoice without manual
work. Adoption is growing fast: one industry study puts it at 10% of corporates in 2023

the most value from AI (Deutsche Bank, citing Coalition Greenwich).

Standards and rules
       Style: REST and JSON, published as an OpenAPI specification, with ISO 20022 data
       elements in payment payloads.
       Security: OAuth 2.0 with OpenID Connect and mutual TLS; the FAPI profile (a
       hardened OAuth profile from the OpenID Foundation, adopted as the security profile
       of the UK Open Banking standard) is the target (Open Banking UK, Nordic APIs).
       Consent and strong authentication: reuse the Berlin Group NextGenPSD2 pattern,
       which defines redirect, OAuth2, decoupled and embedded approaches (Berlin Group
       overview); a payment created by API still needs its checker approval before release.
       Safe retries: an idempotency key on every create call, so a repeated request never
       pays twice.
       Versioning: version in the path, with at least two versions live and a notice period
       before retirement.
       Plans: call-rate and daily call limits per segment, set in the agreement.
       Webhooks: signed, retried and logged, with a replay option.
       Developer experience: sandbox with test data, public API reference, test credentials
       per corporate, and a change log.
       Audit: every call carries a correlation ID and is traceable from the API gateway to the
       core posting.

The CBL national strategy for digital payments points toward open banking and a national
switch, so the API layer is built to be exposed beyond individual corporates later (CBL
strategy).


Core banking integration (Temenos Transact and Oracle
FLEXCUBE)
The corporate platform is a channel: the core banking system stays the system of record
for balances and postings, and the platform owns agreements, limits, approvals and the
corporate experience. The platform talks to the core only through an adapter layer, so a
bank on Temenos Transact (formerly T24) or on Oracle FLEXCUBE gets the same
modules.

Guidelines for every integration
   1. One canonical model: the platform defines its own account, payment, hold and
       customer objects; each core gets an adapter that maps to and from them, so a core
       change never touches modules.
   2. Core posts, platform decides: limits, approval bands and agreement checks run in the
       platform before any call to the core; the core still applies its own overdraft and
       account-status rules.
   3. Synchronous for inquiry and posting, asynchronous for status: balance, account
       validation and internal postings are real-time calls; rail submission, bulk and payroll
       results come back as events.
   4. Idempotency everywhere: every posting carries a unique reference so a retry returns
       the original result instead of posting twice.
   5. Holds on the core: conditional payments and certified cheques place a lien or hold on
       the core account, then release or return it.
   6. Reconcile daily: end-of-day comparison of platform records and core postings, with a
      break report to Payments operations.
   7. Cut-offs and calendar: the platform follows the core's business date, holiday calendar
       and end-of-day window, and queues requests during the core's offline period.
   8. Failure handling: a clear error map from core codes to platform messages, a retry
       queue, and a manual repair screen for the bank.
   9. Security: private network or mutual TLS between platform and core, service accounts
       with least privilege, no corporate credentials in the core.
 10. Release discipline: pin to the bank's core release, run contract tests in a sandbox, and
       repeat performance tests at the peak of salary days.

       digital payments (CBL strategy).
       At a meeting on 5 August 2026, CBL reported mobile-banking transactions of LYD 209
       billion and RTGS transactions of LYD 143 billion (CBL); the period covered was not
       stated in the page excerpt.
       Circular 9/2026 of 11 March 2026 sets new e-wallet transfer limits and allows
       registered foreign residents to use e-wallets (North Africa Post).
