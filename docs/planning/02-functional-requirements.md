# 02 — Functional contract and business invariants

Requirement IDs below are stable. Map each to implementation files and executable evidence. “Must” means an R1 acceptance obligation, including error paths.

## Common security and identity

**SEC-01 Tenant isolation.** A Bank contains Corporates; all corporate objects carry bank and corporate scope. Derive current membership from the verified session. A person can have explicit memberships but must select a permitted context; switching context resets cached data. Bank users require explicit bank permissions and corporate scope. Object IDs never imply authorization. Query by scope and ID together, including downloads, nested resources and background jobs. Return 404 for inaccessible object existence; 403 for a known action denied on an accessible object.

**SEC-02 Permissions.** Model permissions, not `isAdmin`. Corporate roles compose permissions within bank-assigned bounds and per-account grants. Viewer reads assigned accounts; Maker creates transfers; Checker acts only on assigned approval classes/accounts; Treasurer reads cash and may initiate permitted transfers; Finance manages customer data and reports; Payroll officer accesses salary PII; Corporate Admin proposes membership/limits changes but cannot independently grant money authority. Explicit role combinations are supported, while self-approval is still prohibited. Enforce on the server and redact projections before serialization.

**SEC-03 Sessions.** Use a maintained authentication library with database-backed/revocable sessions and secure HttpOnly cookies. Sandbox can use seeded email/password identities with a modern password hash and login throttling; no arbitrary “login as role” endpoint. No default demo credentials active in production. Require CSRF defense and same-origin checks on cookie-authenticated writes. Suspending a user revokes active sessions and blocks pending approvals/execution eligibility. Browser/API authentication providers call the same authorization service. Strong-auth step-up is visibly simulated, never marketed as bank SCA.

**SEC-04 Payroll visibility.** Payroll officer sees row-level names, account identifiers, salary components and payslip reference. Ordinary Checker/Treasurer sees masked file identity, row count, totals, anomalies without employee salary values, policy results and proposal digest. They may approve this aggregate authorization scope; do not grant salary access automatically. Finance/Viewer sees only aggregate counts/status. Bank operations sees opaque row reference and error class; a specifically seeded payroll-support permission can see minimum masked account diagnostics, not full salary. Downloads and error reports use the same projection. Log access to payroll detail/export without logging its content.

**SEC-05 Audit.** Mutations, approvals, policy failures, sensitive reads/exports, credential changes and repairs produce an append-only event with tenant, actor/service, action, target, UTC time, reason, correlation ID, proposal revision, sanitized before/after differences and result. Never log passwords, tokens, upload contents or full employee PII. Successful mutation and audit event persist atomically. Rejected auth attempts produce security events separately. App DB user cannot modify/delete audit rows; use migration privileges separately. R1 proves app-level append-only behavior; this is not certified WORM storage.

## Agreements and administration

**AGR-01 Effective agreement.** Corporate operational modules require an active signed version covering current bank business date/time. Agreement contains segment, permitted module and transaction types, linked debit/credit accounts, currency, per-operation/module/corporate limits, row/item quotas, fees, approval floors, start/end, signer identity and evidence reference/hash. No real signature integration is claimed. Signed evidence references are simulated, labelled and recorded. End is exclusive. Draft/suspended/closed/expired or future agreement blocks new submission and release. Read-only contract/history/support functions remain available to authorized roles even if operational modules are off; governance cannot depend on an already-active agreement.

**AGR-02 Two-person change.** Bank admin maker proposes full immutable revision and diff; a different bank admin checker approves activation or change with reason. Same human cannot bypass by holding two roles. Revision states: DRAFT → PENDING_APPROVAL → APPROVED → EFFECTIVE, or REJECTED/WITHDRAWN; agreement lifecycle is DRAFT/ACTIVE/SUSPENDED/CLOSED with derived expiry. Prevent overlapping effective revisions; keep current active version until successor becomes effective. Activation requires signer evidence and complete required policy. Bank suspension is an audited emergency stop, immediately blocks execution and requires independent review to restore. No hard-delete of history. Concurrent approval uses expected version.

**AGR-03 Module registry.** Store all 33 module definitions as immutable catalogue metadata. A module has delivery status and agreement status separately. Deferred modules cannot be activated through crafted requests; bank console explains unavailable release scope. Segment templates are seed policy starting points, never legally binding defaults. Editing template does not mutate signed contracts. Effective-date changes are bank-admin approvals, not corporate API writes.

**ADM-01 User changes.** Admin can request user invitation/role/account/limit change within signed bank bounds; different eligible Corporate Admin/Checker approves. Do not allow privilege escalation via arbitrary permission names. A grantor cannot grant permission outside their delegated envelope. Invitations use hashed single-use expiring tokens; local inbox transport suffices in sandbox. Disabling access is immediate and audited, re-enabling/privilege increases require approval. A last effective admin cannot be removed without bank-assisted recovery. Corporate cannot modify bank identities.

**ADM-02 Approval rules.** Non-overlapping contiguous inclusive-min/exclusive-max bands per module/type/currency; exact boundary matches one band. At least one independent checker for R1 money movements, even though catalogue allows bank-configured lower controls for some batches: conservative R1 default, explicit product decision. Bank may require two; corporate rules can strengthen but not weaken bank floors. No valid band means fail closed, not zero checkers. Changing the proposal invalidates previous approvals. Agreement/access/policy changes can invalidate release; see APR-03.

## Money, balances and limits

**MON-01 Exact values.** Currency dictionary includes LYD exponent 3, USD/EUR exponent 2 for future compatibility; R1 posting is LYD only. Store bigint integer minor units; API serializes as strings, format in locale at UI only. Reject nonpositive payments, exponent notation, commas in machine amounts, unknown currency, too many decimal digits and out-of-range integers. Do not use floating point or convert bigint to Number for arithmetic. Compare same currency only. No FX aggregation; adding currencies later requires an explicit valuation policy.

**MON-02 Balance authority.** Core adapter owns booked/available balance and core reservations. Platform mirrors inquiries/posting references and workflow, not an alternative real-money system of record. Simulated core uses an isolated ledger and idempotent reservations/postings. Available = booked − active core holds for debit reservations, with no overdraft in R1. Platform limit reservations are distinct from money holds. An internal transfer debits/credits atomically with balanced entries; external payment offsets a simulated settlement control account. Fees offset a fee account. No arbitrary UI balance writes.

**LIM-01 Policy evaluation.** Return a structured explanation for rail ceiling; module/type per-item and daily/monthly; corporate module and overall daily/monthly; user per-item/daily; approval requirement. All applicable constraints must pass, not a numeric minimum across incompatible units. Limits can count amount, items or exposure in full product; R1 executes amount and batch item limits only and rejects unsupported basis. Unset required rail ceiling blocks rail execution with `RAIL_CONFIGURATION_REQUIRED`; unknown is not infinity. Store parameter provenance as DEMO_UNCONFIRMED or BANK_CONFIRMED and effective dates. No source cap is represented as law.

**LIM-02 Usage semantics.** R1 outgoing limits count principal, not fees; balance sufficiency includes principal + fee. This fee/counting decision is explicit and revisitable before pilot. Count each child instruction once at type, parent module and corporate levels, not parent total plus children. Own-account debit counts once toward source corporate totals, not debit+credit. Incoming branch deposits use per-deposit cap and reporting threshold, not outgoing usage. Refunds/returns do not free historic outgoing quota in R1. Daily/monthly windows use `Africa/Tripoli` bank business calendar, with UTC timestamps persisted; month is calendar month, never 30 rolling days. Usage snapshot includes booked and reserved amounts/items and explains remaining capacity.

**LIM-03 Atomic reservation.** Submission/previews are advisory; final approval/release creates or validates durable limit reservations for all applicable counters in one DB transaction. Serialize competing reservations using locked counter rows in stable order (or equivalent serializable transaction with bounded retries). Reserve principal when approved for immediate dispatch; future-dated items reserve on their due business date, not indefinitely at creation. At dispatch recheck policy, permissions, funds and active agreement. Convert reserved to consumed exactly once on confirmed booking; definitive pre-booking failure/cancellation releases reservation. Unknown external result retains reservation and hold until inquiry/reconciliation. A crash cannot release funds/quota merely because a lease timed out. Fresh business-date evaluation must migrate old-window unconsumed reservations atomically before dispatch.

**LIM-04 Fees.** R1 supports fixed LYD fee per child transfer, configurable by type in agreement. Preview discloses fee rule/version, principal, total debit, execution date and estimated available after. Persist the accepted quote. A changed fee after approval produces `REAPPROVAL_REQUIRED`, never quietly charges more. Batch preview totals accepted rows only and includes sum of fees. Exempt own-account transfers can have explicit zero tariff, not missing configuration.

## Single payments and approvals

**PAY-01 Beneficiary.** Scoped list/create/update/archive, normalized account reference and synthetic name enquiry. R1 supports Libyan domestic test account references in a documented sandbox format; do not invent real IBAN validation rules. Store country and scheme and validate according to scheme. Confirmation shows entered vs returned name; mismatch blocks submission until corrected, ambiguous match requires explicit acknowledgment recorded with proposal. Beneficiary edits never mutate historical payment snapshots. Creating a beneficiary does not authorize payment. Real bank account-name APIs are later integration work.

**PAY-02 Proposal.** Wizard: source account → beneficiary/own destination → type/rail → amount/purpose/reference/date → policy and fee preview → immutable submit. Source account and currency from permitted active accounts. Own-transfer destination is same corporate, different account, same currency. Module/type and requested rail combination must be allowed. No client-selected currency overriding account currency; do not auto-fallback to another rail after user review. An execution key, immutable proposal hash, agreement version and policy snapshot persist at submission. Maker may edit draft only; changing pending/approved content creates a new revision and invalidates approvals. A payment cannot be its own beneficiary reference loop.

**APR-01 Approval lifecycle.** State flow: DRAFT → PENDING_APPROVAL → APPROVED → SCHEDULED or QUEUED → PROCESSING → SUBMITTED → SETTLED. Failure outcomes: REJECTED (human), CANCELLED (before dispatch), EXPIRED (approval validity), FAILED (definitive, no booking), STATUS_UNKNOWN (ambiguous), RETURNED (later confirmed return). Reject with reason is terminal for that revision. Do not infer settlement from accepted submission. Timeline records each transition, actor and adapter reference. Own-account execution may skip SUBMITTED after confirmed atomic booking. Illegal/backward transitions fail with conflict.

**APR-02 Distinct authorization.** Checker cannot be the maker or the maker's alternate role in same identity. Unique checker per proposal; repeated click returns existing vote without increasing count. Required checker count and eligible permissions captured in policy; no duplicate vote race. Approve/reject is versioned and idempotent. A rejected revision cannot be released. Bank-admin proposal approvals and corporate payment approvals use separate permission classes.

**APR-03 Revalidation.** At approval, ensure actor is currently active, eligible and within limits. At execution, re-evaluate signed agreement validity/module/type/account, current limits/fees, all approvers' current eligibility and current approval floors. If proposal unchanged but controls tightened, put in action-required state via `releaseBlockCode`; do not release. If approval/fee requirements changed, move back to PENDING_APPROVAL with a new policy revision and no carried approvals. Higher limits do not automatically bypass stored approvals. Cancelling after dispatch is unavailable unless adapter explicitly confirms no posting; offer operations inquiry instead.

**PAY-03 Scheduling.** Single future execution date/time, business-calendar preview, 30-day maximum demo horizon. Persist UTC instant plus business date/time-zone decision. Worker claims only due jobs. ACH has configurable cut-off and closed days; show next eligible execution and ask acceptance if rolled forward. LYPay demo is 24/7 unless simulator outage; own-account respects configured core offline window. At due time recheck policy/funds; insufficient funds produces visible action-required failure, no uncontrolled polling. Recurrence is deferred. Use a test clock; no tests requiring actual midnight.

**PAY-04 Idempotent outcome.** Every create call requires idempotency key; same scope/key/body yields same resource/response; different canonical body gives 409. Core execution reference stable across retries. Timeout after simulated booking leads STATUS_UNKNOWN and inquiry resolves original entry without second debit. No automatic retry of an ambiguous posting with a new reference. A confirmed return records compensating ledger entries and original linkage, not deletion.

## Bulk and payroll

**BAT-01 Import.** Accept UTF-8 CSV and `.xlsx` only (not `.xls`/macros); require template version and headers. Default synthetic cap 100 rows and 5 MiB compressed upload, plus decompressed/worksheet/cell limits; agreement can lower or raise only inside system-tested cap 1,000. These are demo policy decisions, not catalogue row/CBL limits. Server validates content type/signature, bounded parser, formula rejection, duplicate row/reference/account rules, amounts/currency, source permissions and name enquiry. Parse on server, never execute formulas or trust extension. Store file checksum, sanitized metadata and row errors. Reject empty/all-invalid import. Do not log raw file or names/salaries.

**BAT-02 Review.** Rows show valid/invalid/duplicate, stable line number, reason code and proposed amount if authorized. R1 duplicate references within file are errors; repeated beneficiary account is warning for bulk, payroll repeated employee+period+component is error. Return downloadable safe error report. “Continue with valid rows” requires explicit confirmation, exclusion list, accepted-row count/total and a new immutable digest. No invalid row is submitted. Fully identical file warns and links existing run; idempotency/unique line references prevent accidental duplicate release. Same rows with a new file name must not bypass business duplicate checks. Repeat previous batch and saved groups remain deferred.

**BAT-03 Execution.** Whole-batch approval binds accepted row set, account, currency, fees/date and hash. Do not execute rows before approval. Reserve batch total atomically, create child execution records and distribute reservations per row, then execute via worker. Definitive per-row failures release only their reservation; others can settle. Batch derived states: DRAFT/VALIDATING/READY/PENDING_APPROVAL/APPROVED/SCHEDULED/PROCESSING/COMPLETED/PARTIALLY_COMPLETED/FAILED/REJECTED/CANCELLED, with unknown row count separate. COMPLETED requires all accepted rows confirmed settled; never “complete” while any unknown/pending. Totals reconcile from row outcomes. Mixed currencies rejected.

**BAT-04 Retry.** Only definitively failed, never-posted rows may be selected; settled, returned, unknown and in-flight rows excluded. A retry is a new batch linked to parent rows, with fresh approval/limits/fee preview and unique attempt identity. Keep a stable underlying business instruction reference and adapter inquiry before execution. Only one active retry chain per original row; DB enforces concurrency. Unknown rows require operations resolution, not “retry all”. Retrying a business instruction after a confirmed return is a new payment, with explicit business reason, not failed-row retry.

**PYR-01 Employee data.** Payroll officer creates/imports synthetic employees and permitted account mapping; employee ID unique per corporate. Minimal fields: employee code, name, account, active status; no national IDs in R1. Template includes pay period, component (salary/allowance), basic, allowances, deductions, correction and payslip reference. Net = basic + allowances − deductions + signed correction, positive with exact precision; signed components constrained and explained. Draft edits/versioning apply. Account mismatch blocks that row. Compare net to last confirmed same component/pay period baseline; show configured change warning (demo 20%) and acknowledge without revealing salary to unprivileged users. Same employee+period+component cannot settle twice; approved correction requires distinct explicit correction reference.

**PYR-02 Confidential operations.** Salary detail is separate restricted storage/projection; regular payment lists show payroll parent aggregate and masked child references. No employee amount inferred through pagination, account statement descriptions, audit diffs, error messages, activity feeds or notifications. A permitted corporate source-account statement can show aggregate payroll debit; its export must not expose per-employee entries. Simulated core may book child items internally; corporate statement projection groups by approved payroll run without changing accounting totals. Bank support access is scoped and audited. R1 synthetic data is not a substitute for enforcing this rule.

## Collections, deposits, statements and operations

**COL-01 Customer register.** Fields: company-scoped code (immutable once referenced), display name/company, mobile E.164 +218, industry, tags, billing address and collection method. Unique normalized code per corporate, not globally. Imports preview errors before atomic accepted-row commit. Search/filter/sort/pagination, permitted CSV export and audited bulk archive. Open invoice blocks archive; any deposit/history reference requires soft archive, never cascade delete. Customer detail shows deposit count, paid/due amounts from minimal invoice records, pending invoices and activity. Minimal invoice fields: reference, customer, LYD amount/due date/status; invoice creation/edit rights scoped to Finance. No invoicing tax/accounting engine.

**COL-02 Teller matching.** Teller explicitly selects bank-scoped corporate + customer code; code alone cannot identify a corporate. Display corporate legal name, customer name and linked credit account for confirmation. Capture cash/cheque, amount, branch, depositor display reference and uniqueness key; do not collect unnecessary depositor identity. Enforce agreement/type/account and per-deposit cap. Cash-reporting threshold emits a review flag; it is not an invented legal report submission. Amount above demo manager threshold requires distinct Branch manager approval before posting. Teller cannot approve own item even if holding both roles. Manager can only approve assigned branch/bank scope.

**COL-03 Deposit states.** DRAFT → PENDING_MANAGER (if required) → PENDING_POSTING → POSTED for cash. Cheque goes ACCEPTED_PENDING_CLEARING; no available/booked credit until simulator emits clear, then POSTED; returned before clear → RETURNED with reason and no credit. Ambiguous posting → STATUS_UNKNOWN and inquiry. Deduplicate intake and clearance events. Receipt distinguishes pending acknowledgment from posted receipt, carries unique reference, business date, method, masked account, corporate/customer, amount/status and visible synthetic stamp. Never forge official bank certification. Finance sees permitted corporate deposits only; teller sees branch-scoped items only.

**RPT-01 Statements/exports.** Core inquiry projected as intraday and completed-business-day view; filter by account/date/status/reference with cursor pagination. Default deposit window 90 days, max synchronous query 366 days; invalid/oversized ranges rejected. Show booked, available and holds separately with as-of timestamp. CSV and PDF preserve currency/precision, scoped permissions, payroll masking and export audit. Escape spreadsheet formulas and ensure safe filenames/content-disposition; export of unauthorized accounts returns no data. Report resource points to an authenticated download, not a public bucket URL. Long report generation uses jobs and request-time plus download-time authorization.

**OPS-01 Recovery.** Operations dashboard exposes overdue/failed/unknown executions, last attempt and next permitted action. A manual repair requires reason, correct bank scope and independent approval for any financial resubmission. Never edit ledger/balance/status directly. Inquiry may confirm original posting; only safe retry of known unbooked instruction with stable reference is permitted. Record all intervention, not just final success. Reconciliation compares expected postings/amounts/references against simulated core for a business date, emits missing/duplicate/amount/status breaks and immutable resolution history. No auto-delete or “mark all reconciled”.

**ALT-01 In-app alerts.** Seed account low-balance and 80%-usage demo thresholds, editable by permitted Treasurer within bounds. Unique event key per rule/window crossing prevents duplicates on job retry. Alert links authorized account/usage page, no employee data. Read/unread preference is per person. External transports and forecasting remain deferred.

**API-01 Same controls.** Every implemented business action is reachable through REST and shared services. Sandbox corporate credential permits explicit scope/account/module intersection, not checker or bank-admin privilege by default. API-created payments still require human approvals. Bank-admin writes exist under internal authenticated API namespace, never via corporate agreement integration endpoint. Quotas count calls independently of payment amounts; idempotent replay never posts twice.

**EVT-01 Durable events.** Save domain update and outbound event in one DB transaction. Worker signs events, retries safely and records deliveries. At-least-once means duplicate delivery possible; expose stable event ID and replay same business event with new delivery metadata. No payroll PII in payload. Subscriber failure cannot roll back a settled payment. Guard webhook destinations against SSRF (document 04).

## Appendix A — Concrete import templates and field rules

All templates use a manifest/version selected in the upload UI and included in multipart metadata (`templateVersion=1`), not a hidden worksheet macro. For XLSX, worksheet `Instructions` is optional and read-only; data must be in one `Data` sheet with row 1 headers. For CSV, first row is headers, delimiter comma, UTF-8 BOM accepted. Strip BOM only, trim surrounding whitespace in text/code fields, do not remove interior financial characters or guess decimal locale. Excel amount/account cells should be text; reject formula cells even when cached value looks valid. UI can display localized input, but templates use `.` decimal separator and no grouping. Treat numeric account refs as strings to retain leading zeroes; if Excel has already removed digits, reject or require confirmation/correction rather than inventing them.

| Template | Exact required columns | Optional columns |
|---|---|---|
| Bulk v1 | `row_reference,beneficiary_name,account_scheme,account_reference,amount,currency,purpose` | `beneficiary_reference` |
| Employee v1 | `employee_code,employee_name,account_scheme,account_reference` | `active` (`true`/`false`, default true) |
| Payroll v1 | `row_reference,employee_code,pay_period,component,basic,allowances,deductions,correction,payslip_reference,currency` | `correction_reference` (required when a correcting run is proposed) |
| Customer v1 | `customer_code,display_name,mobile,company` | `industry,tags,billing_address,collection_method` |

Bulk `amount` is a positive decimal text in LYD precision. Payroll `pay_period` is `YYYY-MM`; `component` is `SALARY` or `ALLOWANCE`; component amounts are decimal strings, zero allowed except net must be positive. Correction can be signed; correction reference required for corrective business instruction and approval explicitly identifies it as correction. Employee account comes from reviewed employee master snapshot, never free-form extra payroll column. Row reference is unique per corporate business instruction; normal salary identity additionally binds employee+period+component independent of user/file reference.

Customer `tags` uses `|` separator inside quoted CSV cell, max 10 tags of max 32 characters. `collection_method` is `OWN_BANK` in R1; imported `OTHER_BANK` produces a clear unsupported-method error, not silent mapping. Mobile must be normalized E.164 with +218 and valid national-number length according to the chosen maintained phone-number metadata; do not fabricate a regex from the calling code alone. Retain human-facing validation guidance. Company/display name max 160, purpose max 140, references/codes max 64 printable safe characters, billing address max 500. Reject embedded NUL/control characters, invisible direction-control characters in bank/account codes, duplicate headers and unsupported/missing columns. Unknown optional metadata does not get written to domain entities automatically.

Sandbox account format must be explicitly documented (example scheme `DEMO_DOMESTIC`, reference `DEMO-LY-000001`). This format is not a real IBAN or a CBL standard. Permit only seeded/validated sandbox accounts; cross-corporate recipient references are allowed as payment beneficiaries only through authorized name-enquiry, never as source/account grants. XLSX file row/cell strings are bounded (max 10,000 characters per raw cell before domain-specific limits), decompressed total default 25 MiB, at most 2 sheets including optional Instructions, no embedded objects/macros/external links. System hard cap of 1,000 data rows still applies even if upload file is small. Document parser-specific enforcement and adversarial tests.

## Appendix B — Permission intersections

Permission is the intersection of active person/session or credential, active membership, bank/corporate scope, role permission, account grant, agreement entitlement, type/rail availability and current policy/state. Do not use a single “role rank” to bypass these layers.

| Action | Default allowed identity | Additional constraints |
|---|---|---|
| Read account/statement | Viewer, Finance, Treasurer, granted Maker/Checker | Assigned account; payroll projection always enforced |
| Draft/submit payment | Maker or Treasurer with type permission | Debit account grant; user limits; agreement/type |
| Approve payment | Checker | Independent human, approve-account grant, matching approval class |
| Prepare/inspect payroll | Payroll officer | Restricted employee/payroll detail permission; aggregate funding rights don't imply it |
| Approve payroll aggregate | Checker | Payroll approval class and debit grant; no automatic salary row permission |
| Customer/invoice manage | Finance, Corporate Admin if explicitly granted | Same corporate, module active for writes |
| Teller capture | Branch teller | Same bank and assigned branch, scoped corporate entitlement |
| Threshold deposit approval | Branch manager | Same branch scope, different human from teller |
| Propose agreement/rail change | Bank admin maker | Bank scope and full proposal evidence |
| Approve bank governance | Bank admin checker | Different proposer human, exact revision |
| Propose corporate grants/rules | Corporate Admin | Within bank and delegated envelope, second approver |
| Repair financial execution | Payments operations proposer + independent eligible bank checker | Known safe recovery only, reason/evidence; no arbitrary balance override |
| Audit/exports | Explicit Finance/Compliance/audit permission | Scoped data, payroll redaction; sensitive read/export logged |

Permissions may be combined intentionally but never defeat actor separation. Keep this matrix executable in permission-map tests rather than duplicating ad hoc checks in every page.
