# Runbook — Al Qarib GTB sandbox

Everything here was run in the implementation environment unless a line says **not executed**.
The product is a sandbox: synthetic people, synthetic money, a simulated core and simulated rails.
Nothing in this file connects to a bank, a payment rail, an e-mail or an SMS service.

Evidence for the commands below (exit codes, counts, tested revision) is in
[docs/audit/IMPLEMENTATION-REVIEW.md](audit/IMPLEMENTATION-REVIEW.md).

## 1. What you need

| Tool | Version used | Note |
|---|---|---|
| Node.js | 24.22.3 (`.node-version`; `engines` accepts 24.11 – <25) | |
| pnpm | 10.28.0 (`packageManager`) | `corepack enable` selects it |
| PostgreSQL | 16.15 | 16 or newer; the `btree_gist` extension must be installable |
| Chromium for Playwright | 1.63.0 | only for `pnpm test:e2e` |

Ports: the app listens on `3000` (`PORT` changes it); the browser tests start their own copy on
`3100`. Private files (uploads, reports, receipts) are written under `STORAGE_PATH` (`./storage`),
which is outside the public web root and ignored by Git.

## 2. First-time setup

Run from the repository root.

```bash
pnpm install --frozen-lockfile
```

```bash
pnpm setup:env
```

`setup:env` writes a private `.env` (mode 600) from `.env.example` with freshly generated secrets
and a generated demo password. It prints no value and never overwrites an existing `.env`.

Provide PostgreSQL in **one** of two ways.

**A. A local PostgreSQL 16 cluster (the path used here).** Needs `sudo -u postgres psql` or root.

```bash
pnpm db:local
```

**B. Docker (not executed here — no Docker daemon).** Add `POSTGRES_ADMIN_PASSWORD=<any local value>`
and `POSTGRES_ADMIN_URL=postgresql://postgres:<the same value>@127.0.0.1:5432/postgres` to `.env`, then:

```bash
docker compose up -d db
```

```bash
pnpm db:local
```

Either way `db:local` creates two roles and one database and drops nothing: `alqarib_owner` owns the
schema and is used only for migrations; `alqarib_app` is the least-privilege role the app and worker
use (no DDL; it cannot update or delete audit rows). The `POSTGRES_ADMIN_URL` path was executed
against the local server over TCP; the compose file itself was not.

```bash
pnpm db:migrate
```

```bash
pnpm db:seed
```

The seed refuses to run unless `APP_MODE=sandbox` and `SEED_DEMO_ENABLED=true`. Running it a second
time creates nothing ("0 identities created, 0 opening balances booked").

## 3. Run the product

Two processes are always needed: the web application and the worker. Payments are approved in the
application and **posted by the worker**; without a worker an approved payment waits as
*Queued for execution*.

Development:

```bash
pnpm dev
```

```bash
pnpm worker:dev
```

Compiled, as a deployment would run it (this is what the browser tests and the smoke test use):

```bash
pnpm build
```

```bash
pnpm start
```

```bash
pnpm worker:start
```

Check that both are up:

```bash
curl -s http://localhost:3000/api/v1/health/ready
```

```bash
pnpm worker:status
```

`/health/ready` reports database access, migration level and adapter mode and nothing else.
`worker:status` prints the last heartbeat, the queue, executions with an unknown outcome and event
delivery counts (counts only); it exits 1 when no worker reported in the last 30 seconds.

Then run the business smoke test (section 6). To stop: end the two processes you started
(`Ctrl+C` in their terminals). Nothing else is started for you, and nothing survives a reboot.

## 4. Demo people

All identities are synthetic and exist only in a sandbox database. They share one password: the
value of `DEMO_PASSWORD` in **your** private `.env` (generated by `pnpm setup:env`). Read it locally:

```bash
grep '^DEMO_PASSWORD=' .env
```

There is no "log in as role" switch: sign out and sign in as another person. Addresses end in
`@demo.alqarib.test`.

| `bank.dual` | Bank A | Both bank administrator roles | Show that holding both roles does not allow self-approval |

| `rm` | Bank A | Relationship manager | Read corporates |
| `payroll.support` | Bank A | Payroll support | Operations view with a masked account for payroll lines |
| `teller1` / `manager1` | Bank A, branch BR1 | Teller / branch manager | Capture a deposit / approve one above the threshold |
| `teller2` / `manager2` | Bank A, branch BR2 | Teller / branch manager | Show branch scope |
| `branch.dual` | Bank A, branch BR1 | Teller + manager | Show that a person cannot approve their own capture |

## 5. Walkthrough: one complete payment with distinct people

`pnpm smoke` performs exactly this through the API. In the browser (English `/en/...`, Arabic `/ar/...`):

1. **`bank.maker`** → Bank → Corporates → *Qarib Trading Demo* → Agreement → *Propose first agreement*
   (later revisions: *Propose revision*). The form starts from the segment template; add the
   simulated signature evidence and submit.
2. Still as `bank.maker`, open Bank → Approvals: the proposal cannot be approved by its proposer.
3. Sign out. **`bank.checker`** → Bank → Approvals → open the proposal, review the terms, approve.
   The agreement is now in force.
4. Sign out. **`a.maker`** → Payments → *New payment*: source *Operating*, beneficiary
   *Tripoli Office Supplies Demo* (name check: matched), amount `125.000`, a purpose. The review
   step shows amount LYD 125.000, fee LYD 0.500, total debit LYD 125.500, one approval needed. Submit.
5. Still as `a.maker`, open the approval: there is no approve control for the maker.
6. Sign out. **`a.checker1`** → Approvals → open it. The page shows the recipient, amount and fee
   exactly as submitted. Approve.
7. The worker posts it within a few seconds: the payment moves from *Queued for execution* to
   *Settled* and shows its instruction reference.
8. As `a.maker` or `a.finance`: Accounts → *Operating*: the balance is LYD 125.500 lower and the
   statement has a payment line (−125.000) and a fee line (−0.500) with that reference.
   Limits and usage: used today rose by LYD 125.000 (the fee does not count toward limits).
9. As `a.admin` or `a.finance`: Audit → search the payment reference: created, submitted, approved by
   a different person, processed and settled by the worker — all for the same instruction.

Repeating a request does not repeat the money movement: every create/approve call carries an
idempotency key; the same key and body returns the first result, the same key with another body is
refused (409). `pnpm smoke` checks both, and that the balance does not move again.

### Other journeys

| Journey | People | Where |
|---|---|---|
| Lost response after posting → "result being checked" → inquiry → one debit | `a.maker` pays *Response Lost Logistics Demo*, `a.checker1` approves, `ops` inquires | Bank → Operations |
| Bulk transfer: upload CSV/XLSX, exclude invalid rows explicitly, approve the total, partial result, retry failed rows as a new batch | `a.maker`, `a.checker1` | Batches (templates on the upload page) |
| Payroll: officer sees every line, checker approves the total only, statement shows one line per run | `a.payroll`, `a.checker1`, `a.finance` | Payroll |
| Branch deposit by customer code: capture, manager approval above LYD 2,000, receipt; cheque credits only after clearing | `teller1`, `manager1`, `ops` (cheque events), `a.finance` | Bank → Teller, Bank → Simulator, Deposits |
| Reconciliation with an injected difference | `ops` | Bank → Simulator (extract overlay), Bank → Reconciliation |
| Invitation approved by a second person | `a.admin`, `a.checker2` | Administration → Users |
| API token and signed webhook | `a.admin` | Developer; [docs/api/webhooks.md](api/webhooks.md) |

Synthetic recipients with a fixed behaviour (all at simulated banks): `DEMO-LY-900001` succeeds,
`…900002` name mismatch, `…900003` blocked account, `…900004` response lost **after** booking,
`…900005` no answer **before** processing, `…900006` slow ACH, `…900007` late return, `…900008`
close name match, `…900009` duplicate rail event, `…900010` out-of-order rail events, `…900011`
rejected by the rail. `DEMO_DOMESTIC` / `DEMO-LY-nnnnnn` is a sandbox account format, not an IBAN
and not a CBL standard.

## 6. Smoke test and restart check

With the application and the worker running:

```bash
pnpm smoke
```

It signs six distinct people in, activates the agreement if none is in force (proposer refused,
second administrator approves), makes the LYD 125.000 payment (maker refused, checker approves),
waits for the worker, and fails unless: the balance fell by LYD 125.500, usage rose by LYD 125.000,
statement/timeline/audit carry the same instruction reference, and repeating the approval and the
create request changes nothing. It creates one payment per run and prints no secret.

Restart check — proves that nothing is lost or doubled across a stop. Stop the worker, wait 30
seconds, then:

```bash
pnpm smoke --restart-check
```

It approves a payment while no worker runs, verifies it waits as `QUEUED` with the balance
untouched and the limit reserved, and then waits for you to start the worker (you may also stop and
start the application). It passes only if the restarted worker posts the payment exactly once.

## 8. Sandbox controls (bank operations only)

Bank → Simulator, signed in as `ops`, or the `/api/v1/bank/simulator/*` operations:

- **Clock**: move the sandbox business clock forward (cut-off, scheduling, settlement delays). It
  is an offset stored in the database and applies to the whole sandbox.
- **Availability**: switch the simulated core, LYPay or ACH offline. Balances then show "not
  available" with the time of the last answer — never zero.
- **Faults**: arm a one-off timeout or rejection for one instruction reference.
- **Extract overlays**: make the reconciliation extract differ from the ledger (hide, duplicate,
  change an amount) so breaks can be demonstrated. The ledger itself is never edited.
- **Cheques**: clear or return a pending cheque.

Every use is written to the audit trail. None of this exists outside `APP_MODE=sandbox`.

## 9. Installing on a phone or desktop (PWA)

- Installation needs HTTPS (or `localhost`) and the production build; development never registers
  a service worker.
- Chromium browsers offer *Install app* in the app header and on the *More* page. On iPhone/iPad
  use Safari → Share → *Add to Home Screen*; the app explains this instead of promising an install
  button. Using the product in a normal browser tab always works.
- **Installing does not enable offline banking.** The service worker stores only the generic
  offline page and the icons. It never stores or answers API calls, sign-in, page HTML, statements,
  payroll, reports or downloads, and it never queues a payment or an approval. Offline, an open page
  hides its financial content and disables actions until the connection is back.
- **Updates**: a new version waits. The app shows "Update available"; it never reloads under an
  open form, a review or a request in flight.
- **Developers — remove the worker and its cache**: browser DevTools → Application → Service
  workers → *Unregister*, then Application → Storage → clear *Cache storage* entries named
  `alqarib-public-*`. Do not clear other site data.
- A web app cannot prevent screenshots or delete a PDF someone saved. Receipts and reports are
  authenticated downloads; what a person saves is theirs.
- **Not verified on physical devices.** Android Chrome installation (P-02), iPhone Safari
  Add-to-Home-Screen (P-03), real file pickers and on-screen keyboards, and browsers other than
  Chromium (P-12) are pending. See the status file.

## 10. Reset, backup, restore

Rebuild the local sandbox database from nothing (drops it; refuses unless the database is local,
its name ends in `_dev`, `_demo` or `_test`, the mode is sandbox and `--yes` is given):

```bash
pnpm db:reset-demo --yes
```

Backup and restore of the synthetic data (documented, **not executed as a drill**; no claim about
bank-grade recovery). `MIGRATION_DATABASE_URL` is the value from your `.env`:

```bash
pg_dump --format=custom --file=alqarib_dev.dump "$MIGRATION_DATABASE_URL"
```

```bash
pg_restore --clean --if-exists --no-owner --dbname "$MIGRATION_DATABASE_URL" alqarib_dev.dump
```

Copy `STORAGE_PATH` alongside the dump: report and receipt files are referenced from the database.
After a restore run `pnpm db:migrate` to re-apply the runtime grants.

## 11. API

- Contract: [docs/api/openapi.json](api/openapi.json) (116 operations), also served at
  `/api/v1/openapi.json`. `pnpm openapi:check` fails when code and file differ.
- Webhooks: [docs/api/webhooks.md](api/webhooks.md).
- A token is created in Developer by a person who is both corporate administrator and API
  integrator (`a.admin`). It is shown once. It can read what its scopes and accounts allow and can
  prepare a payment; it can never approve, administer, read payroll or reach the bank workspace.

Example (replace the placeholder with a token you created; never commit one):

```bash
curl -s -H "Authorization: Bearer $ALQARIB_SANDBOX_TOKEN" http://localhost:3000/api/v1/accounts
```

```bash
curl -s -X POST http://localhost:3000/api/v1/payments/preview -H "Authorization: Bearer $ALQARIB_SANDBOX_TOKEN" -H "Content-Type: application/json" -d '{"moduleId":"1.1","transactionType":"INSTANT_ACCOUNT_CREDIT","sourceAccountId":"<account id>","beneficiaryId":"<beneficiary id>","amount":{"currency":"LYD","minor":"125000"},"purpose":"Example","clientReference":"EX-1","execution":{"mode":"IMMEDIATE"}}'
```

Amounts are strings of integer minor units (`"125000"` is LYD 125.000). Every create or command
`POST` needs an `Idempotency-Key` header; errors are `application/problem+json` with a stable `code`.

## 12. When something is wrong

| What you see | Cause | Do |
|---|---|---|
| A payment stays *Queued for execution* | No worker | `pnpm worker:status`, then start the worker |
| "No effective signed agreement covers this action" | Corporate A's agreement is still a draft | Walkthrough steps 1–3, or `pnpm smoke` |
| "Result being checked" on a payment | The simulated core did not answer; the outcome is unknown | `ops` → Bank → Operations → *Inquire*. It is never retried blindly |
| Balance "not available" | The simulated core is switched offline | Bank → Simulator → Availability |
| An ACH payment says it will run on the next business day | After the 14:00 Africa/Tripoli cut-off or a closed day | Accept the shown date, or move the sandbox clock |
| Integration tests stop with "PostgreSQL is not reachable" | The server is down | Start PostgreSQL (`pnpm db:local` starts a stopped local cluster) |
| `pnpm test:e2e` says it needs the production build | No build | `pnpm build` |
| Sign-in is refused after several wrong attempts | Five wrong attempts within 15 minutes lock that address for 15 minutes (the answer is the same whether or not the address exists) | Wait, or use another demo person |
